Loops and skills

The while-loop that turns a text predictor into a worker, and procedure packaged as files it can load.

Nothing in the transformer acts. It reads tokens and emits tokens, once, and stops. Everything agentic about an "agent", the file edits and the test runs, comes from a plain while-loop around that function. A piece of ordinary software called the harness runs that loop. The loop is small enough to sketch in full:

context = [system_prompt, tools_schema, user_request]
while True:
    output = model(context)          # one forward pass per token
    if output.is_answer:
        return output                # the model chose to stop
    result = execute(output.tool_call)
    context += [output, result]      # both are just tokens

Two things about this loop repay attention. The model never executes anything: it emits a tool call as text, the harness runs it, and the result comes back as more text. And the context grows every lap, so a long-running loop inherits every property of the context window from the first piece. The cost of re-reading grows, retrieval degrades in the middle, and eventually compaction throws away detail. Loops do not escape the window; they run inside it.

The difference between a loop that converges and one that thrashes is mostly the lap body. Verification belongs inside it. An agent that runs the tests after each edit gets real feedback every lap. An agent that edits five files and tests at the end spends four laps guessing. The result tokens are the only steering input the model gets. Make them informative and the loop self-corrects; leave them silent and it drifts.

Loops also need a reason to stop. Well-behaved harnesses enforce step caps and token budgets on top of the model's own judgment. A model that keeps finding one more thing to check will happily spend your budget being diligent. The stop condition is part of the task definition, so state it explicitly.

Loops that outlive the session

Some loops run longer than any single context: the nightly dependency triage, the agent that watches CI and files issues, and the recurring cleanup pass. Two mechanics change at that scale. Scheduling moves to the harness. Either a cron-style trigger starts a fresh agent on a timer, or the agent runs self-paced: it finishes a pass and schedules its own wake-up. And state must live outside the model, in files it re-reads on every wake. The weights are frozen and the old context is gone. Whatever the loop learned last night exists only if the loop wrote it down. A recurring agent without externalized state re-derives the world from scratch every morning.

The rule of thumb for pacing came up in the effort piece in another form: match the spend to the signal. A loop that polls every minute for a state that changes daily burns budget and observes nothing. When the harness can notify on events, an event-driven loop beats polling outright.

Skills: procedure as files

Once agents run in loops, you start retyping the same instructions. How this team deploys. How to run this repo's flaky test suite. The incident checklist. The obvious fix, pasting all of it into the system prompt, works and then quietly gets expensive. Every request pays tokens for every procedure, relevant or not. The pile grows until it competes with the task for the model's attention.

A skill is the packaged alternative: a named file of instructions, optionally with reference docs and scripts alongside. The harness registers it under a one-line description. The economics are progressive disclosure. The index of descriptions rides along in every context at a few tokens per skill; the full instructions load only when a task matches. A library of 40 procedures costs a few hundred always-on tokens instead of 40,000.

Because a skill is a file, it inherits everything files already do well. It lives in a repo, versioned and reviewable in a pull request. Editing it changes the agent's behavior on the next run, with no retraining and no deploy. Copy a directory, and a teammate's hard-won procedure becomes your agent's procedure. Compare the alternatives: fine-tuning bakes procedure into weights where nobody can read or patch it, and prompt-stuffing pays rent on every request. Files sit in the sweet spot, cheap to change and auditable by anyone who can read.

It helps to keep the three kinds of instruction distinct, because they fail differently when you mix them. The prompt states the task at hand. Memory holds durable facts about this project and this user. A skill holds a reusable procedure for a kind of task. When procedure leaks into memory or you bake tasks into skills, the agent starts applying yesterday's specifics to tomorrow's work.

Loops and skills compose

The two ideas meet in the recurring agent: a scheduled loop whose body is a skill. The cron entry says "every night at 2:00, run the dependency triage skill". The skill says what triage means here: which manifests to check, what counts as urgent, where to file findings, and what to write down for tomorrow's run. The schedule is configuration and the procedure is prose, both in version control and both editable in 30 seconds. A surprising amount of operational automation reduces to this shape.

Working defaults

  • Write the skill the second time you type the same instructions. The first time is a task; the second is a pattern with a third occurrence coming.
  • Spend effort on the description line. It is the only part the model sees when it decides whether to load the skill, so a vague description is an unreachable skill.
  • Give every loop a budget and a stop condition, and put verification inside the lap rather than after it.
  • For anything recurring, decide what the loop writes down for its future self. That file is the loop's memory, so give its format the same care as the schedule.

One layer sits under all of this: the harness itself, the software that owns the loop, the tools, the permissions, and the context budget. That piece is next in the series.
